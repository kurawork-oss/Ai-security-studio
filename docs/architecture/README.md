## 設計の 3 原則

1. **データ最小化 (Data Minimization)** — 生の PII は永続化しない。ログにはメタデータのみ。
2. **フェイルクローズ (Fail-Closed)** — 匿名化に失敗したら LLM へは絶対に転送しない。
3. **拡張性優先 (Extensibility First)** — プロバイダー・PII ルールは後から自由に追加できる設計。

## 承認が必要な主要な設計判断（Open Decisions）

実装前に方針を確定したい論点です。特に指定がなければ「推奨」で進めます。

| # | 論点 | 推奨（デフォルト） | 代替案 |
| --- | --- | --- | --- |
| D-1 | MVP のテナント単位 | **組織(organizations)を最初から導入**（B2B 前提・RLS 設計が綺麗） | 個人ユーザー単位で開始し後で組織化 |
| D-2 | 匿名化方式 | **不可逆プレースホルダ**（`<PERSON_1>` 等）を既定 | 可逆トークン化（Vault）はフェーズ2 |
| D-3 | Analyze の再識別 | **リクエスト内一時マップで復元可**（永続化しない） | 常に匿名のまま返す |
| D-4 | バックエンド DB アクセス | **SQLAlchemy 2.0 async + Alembic**（Repository を綺麗に実装） | supabase-py / PostgREST |
| D-5 | 秘密鍵の暗号化 | **AES-256-GCM エンベロープ暗号（KEK は環境変数/KMS）** | Supabase Vault |
| D-6 | モノレポ管理 | **pnpm workspaces + Turborepo** | 個別リポジトリ |

各判断の詳細は該当ドキュメント内に記載しています。
